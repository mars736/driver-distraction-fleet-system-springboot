# 告警人工处理

实现架构第九节中的告警确认、撤销和人工处理记录，不回流模型。使用现有两种角色，管理员处理全部告警，司机只读本人告警及处理记录。

## 数据库升级

新增第八张表 `alert_review_record`，保存告警 ID、处理前后状态、原因、操作人 ID / 账号 / 姓名快照、北京时间操作时间。已有 `alert_record.status` 字段足以保存状态，不修改其他告警数据。

- 新数据库执行 `src/main/resources/db/schema.sql`。
- 已有七张表的数据库执行 `src/main/resources/db/migrations/20261111_alert_review.sql`，可重复执行，不删除、不改写已有记录。
- 应用不自动执行建表脚本；本机开发库已执行该增量脚本。

## 接口与状态

所有请求携带 `Authorization: Bearer <token>`。

| 方法 | 地址 | 权限与返回 |
| --- | --- | --- |
| POST | `/api/alerts/{id}/reviews` | 仅管理员；返回本次处理记录 |
| GET | `/api/alerts/{id}/reviews` | 管理员全部、司机本人；返回处理记录数组，时间及 ID 倒序 |

请求示例：

```json
{
  "status": "CONFIRMED",
  "reason": "人工核实关键帧，确认存在手机分心行为"
}
```

撤销时 `status` 为 `REVOKED`。原因必填，最长 500 个字符，保存时去除首尾空白。操作人和时间从服务器取得，不接受客户端指定；操作人账号改名后，历史快照保持不变。

本阶段只允许 `OPEN → CONFIRMED` 或 `OPEN → REVOKED`。已处理记录不允许重复确认、重复撤销或反向覆盖，返回 HTTP 409 和 `{ code: 409, message: ..., data: null }`，客户端应刷新详情。未来申诉需要另行定义可追溯的复核流程。

同一告警通过 MySQL 行锁串行处理，条件更新状态和插入历史位于同一事务。两位管理员并发处理时只有一个成功，另一个返回 409。历史写入失败时状态一起回滚，可以重新提交。

参数无效、状态为 OPEN、空白原因、JSON 无法解析返回 HTTP 400；未登录或失效 token 返回 401；司机尝试写入返回 403；记录不存在或司机访问他人处理历史返回相同的 404。未处理告警的历史为成功的空数组。告警模块执行异常返回 HTTP 500 和通用 Result，不向客户端暴露数据库异常内容。

列表接口 `GET /api/alerts` 新增 `status=OPEN|CONFIRMED|REVOKED` 筛选，可与其他筛选组合。详情中的 `status` 即当前处理状态，司机可读。

## 业务边界

人工处理不删除关键帧、不修改识别元数据、不改变判定累计和短信投递状态，也不会补发短信。确认或撤销 `SPEED_UNKNOWN` 仅表示处理速度异常，仍然不是分心违规。查询中的 `violation` 表示记录类型是否属于分心行为，处理有效性需同时查看 `status`；本阶段没有评分或扣分，撤销回补会在评分与申诉模块中接入。

本阶段处理记录按告警归属控制访问，司机可见管理员操作人快照和处理原因；不新增第三种角色。
